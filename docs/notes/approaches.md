# アプローチのメモ

## 手法
1. ベースライン
2. 源流の入力画像を待機列のみが映るようにROI処理
3. 人物をオブジェクトではなく顔で検出
4. 人物を顔ではなく骨格(ポーズ)で検出
5. オブジェクト検出で人物を列挙(低い信頼度) → 切り取って(ROI処理して)、ポーズ検出で人物に絞る
  - 実用に耐えうる信頼度でフィルター
  - 後ろ姿対策と、後のアプローチの体の向き検出を兼ねてポーズ検出を採用
  - MoveNet Lightningを採用
  - 画像の切り出しは　固定サイズの非表示キャンバス + `createImageBitmap`でバウンディングボックスの範囲で指定で切り出し を実行して、ワーカー間では所有権移転で無駄を削減
  - ワーカーマネージャーからワーカーに、初回時に元画像のサイズを渡して固定キャンバスのサイズを決める
  - 密集もあり得るので切り取る時にマージンはつけない
  - 人数が多い場合があるので、ワーカープールは必須
  - トラブルを防ぐため、ワーカープールの数は固定(4コアが目安)
  - 源流の`Promise.all`でバウンディングボックス列挙で出た候補を同時にワーカーマネージャーに投げる
  - 源流の`Promise.all`の段階では元のバウンディングボックスを生成したキャンバスに触れるので、そこから候補分をビットマップで切り出す
  - 源流の`Promise.all`で処理結果を元画像の座標に直す
6. 切り取ったのがモデルの入力用として小さすぎる場合は拡大
  - 固定キャンバスの数を集約するため、源流(`detectPeople.ts`)の`Promise.all`の子の中ではなく、ワーカーで行う
  - ワーカーごとに、小さすぎるビットマップが来た時のための固定キャンバスを持つ(もちろんグローバルで使い回し)
  - 拡大して十分なサイズにするのが目的なため、固定キャンバスのサイズは元の画像のサイズではなく、処理に十分とされるサイズを流用
  - サイズが十分な場合は行わない
  - 人物の低い信頼度による列挙の後の、ポーズ検出の前の段階で実行
  - 拡大した比率などから検出結果のポイントを本来の数値を計算する(数式はなくても、説明資料で触れるべきところ)
  - これによりポーズ検出の精度向上が見込まれる
7. 重複対策
  - 正常かどうかに関わらず、骨格のポイントを使ってマージンをつけてROI処理して保持
    - ポーズ検出で骨格が出たら、その骨格のポイントにマージンをつけてバウンディングボックスとして切り取る
    - これにより領域の中で最も目立った人物だけがバウンディングボックスとして残る
    - さらに、かなり余白があるけど検出自体はうまく行ったのも捨てずに助けることができる
  - 最後に、残った各人物のバウンディングボックスの重なりを調べて、重複はバウンディングボックスが大きい方を残す
    - 領域の重なり具合で判定(数式はなくても、説明資料で触れるべきところ)
    - この「大きい方」というのは別人ではなく、同じ人物で大きい方(写りが良いと思われる方)
8. 縦方向の乱立対策
  - 全ての人物のバウンディングボックスの検出が終わった後の、重複対策の後に行う
  - 画像中で人物とされた中で、画像のY方向の重なりも調べ、重なり具合が閾値を超えたらバウンディングボックスを結合
  - 重なり具合の判定は、バウンディングボックスのX座標が閾値を超えて被っていたら乱立判定
  - これにより、対策をすり抜けた、サイズは小さいがポーズ検出はパスした小さく、縦方向に乱立したバウンディングボックスを正せる
  - パフォーマンス最適化
    1. WebGPUを使用(利用できる場合は)
    2. WebGL環境を最適化
      1. `tf.env().set('WEBGL_RENDER_FLOAT32_CAPABLE', false)`と`tf.env().set('WEBGL_FORCE_F16_TEXTURES', true)`、それぞれ対応しているかの判定で16ビット推論を使用
      2. 毎回入力される画像は内容もサイズも異なるので、`tf.env().set('WEBGL_DELETE_TEXTURE_THRESHOLD', 0)`で無駄なキャッシュの蓄積をブロック
9. 人物から向き取得 & 距離でグループ判定
  - 人物から向き取得
    - 乱立対策で人物のバウンディングボックスが最終決定するので、その後に行う
    - 同じくMoveNet Lightningをマネージャー経由で使用
    - これに伴い、ワーカーやマネージャーを骨格の座標の取得に対応させる
      - マネージャーのキューの追加メソッド(`processCandidate`)を、人物検出用とポーズ検出用を用意する
      - ポーズ検出用は純粋な骨格の座標取得用で1人が前提で、複数人の対応は不要
      - ワーカーも対応させる(共通部分はどうにかする、もちろんOOM対策継続)
    - MoveNet Lightningの2Dポイントから、映像中でのベクトルを求める(後ほど使う、getGroups/index.tsから外にエクスポートするわけではなく、内部の処理で使う)
    - これに対応するため、トップレベルのtypes.tsにPerson型(interface、全てのプロパティが任意(`?`)である)追加&周辺修正(detectPeopleも対応させる)
      - Person型はバウンディングボックス持ち(既存のバウンディングボックス)
      - 骨格の座標(ポーズの検出結果のもの)
      - 体の向きも持つ
    - detectPoses.tsで`Promise.all`で1人ずつの切り取り済みの画像を受け取ってマネージャー投げて、返ってきた骨格の座標から体の向きも求める(同じファイル内に向きを求めるメソッドも作成)
    - トップレベルのindex.ts内で、`detectPeople`の後に、処理結果をそのまま`detectPoses`に投げる
  - 距離でグループ判定
    - 全体の人物の分布(バウンディングボックスの配置)と、人物の向きから列を、1つの線として抜き出す(アルゴリズム)
    - バウンディングボックスに加えて人物の向きも織り込むことで、非常に横に長い列が存在しても対応できる
    - その列の向きに対して横並びはグループ(アルゴリズム)
    - 各人物が持っているバウンディングボックスの位置で判断
    - これにより、人物を誤魔化してグループ化するconvertToGroupsを卒業(削除)
    - groupPeople/
      - index.ts
      - estimateQueueLine.ts
      - groupByDistance.ts
10. 検出モデルの刷新(ONNX Runtime WebでYOLOv12 Nanoに移行)
  - 精度大幅向上が見込まれる
  - 重複排除の方法丸ごと違う(アプローチ3〜8と全く違う)
    1. YOLOv12 Nanoは精度が高いので信頼度を設定(例: 0.25)して検出(`dispose`メソッドなどで確実に蓄積を防ぐ、オプションでアリーナ制限を無効化)
    1. まず検出されたバウンディングボックスをX座標順で並び替える
    2. バウンディングボックスを順番に当たって、横が閾値(例: 8割)以上重なっていたら(位置と幅の両方で閾値以上重なったら、内包はカウントされない、内包を直接弾くわけではくこの通りに実装されればそうなるという例、例えば大きいバウンディングボックスの横が小さいバウンディングボックスを完全に収めていても除外)まとめる
    3. 被っていなかったらその作業していたグループを1人の人物として確定する
      - 縦のサイズは全てのバウンディングボックスを内包
      - 横のサイズも全てのバウンディングボックスを内包
      - 人物のバウンディングボックスとして使われたバウンディングボックスは、大元のバウンディングボックスの配列から削除
    4. その人物のグループ化を終了して、次の人物のグルーピングに移る(つまりループ)
  - MediaPipeと違ってDOM依存がないのでワーカー移行(同じくワーカーマネージャーが管理)
  - 重複排除の方法が変わったことで、ポーズ検出ワーカーの`PROCESS_CANDIDATE`は廃止
  - getGroups (ルート)
    - workers
      - workerManager.ts (新たに人物検出も管理)
      - peopleDetectionWorker.ts (新規、実際の処理はここで行う)
    - detectPeople.ts (バレルファイル持ちのディレクトリからファイルに変更、エントリーポイントに役目を変えて存続)
    - deduplicateDetections.ts (削除)
11. 待機列では前後で跨ぐグループもいる → 距離だけでなく体の向き(スマホなどを操作している可能性も考慮して顔の向きは使わない)でグループ判定
  - 体の向きは、人物ごとに持っている映像内でのベクトルを利用
  - 隣り合う前後をチェックして(前後のグループの人物しか比較しない)
  - それぞれの人物の体の向き(ベクトル)の延長線の交差の角度を閾値で判断してグループ判定(アルゴリズム)
  - 延長線の交点が閾値以上(例: 比較している2人のバウンディングボックスの横幅の平均の2倍)離れてたら、交差していてもグループ化しない
  - 横並びの誰か1人でも前または後ろの列のグループの向いていたら連れ(グループ)判定
  - 該当例
    - 壁に寄る配慮をして、前後で会話をしているカップル
    - 部活で複数人で並び、前後で跨って会話してる人達
    - トイレで連れに先に並んでもらっていた場合で、後から合流してそのまま話す
  - getGroups/groupPeople
    - index.ts (体の向きによるグループ化を追加)
    - groupByOrientation.ts (新規追加)
12. 通行人による誤検出を避けるため前後のフレームの情報も組み合わせる
  - 先に言っておくが、2の段階で元から待機列の部分でカットされているため、通行人は処理用映像の端に頭程度しか映らないが念のため対策
  - 直近のフレームのみ保存(詳しくは`TrackedPerson`)
  - measureFps.ts (ファイルのトップレベルで状態を管理・保持して、どのファイルから呼ばれても共通になるようにする、直近(基準のフレーム数)のタイムスタンプのみ保持、タイムスタンプの保持に`Float64Array`用のリングバッファのクラスを使用)
    - updateFpsメソッド (タイムスタンプを渡す、主に`performance.now()`)
    - getFpsメソッド
  - 待機列の追跡(通行人を除外した待機列の人物だけに絞られた配列の維持、アルゴリズム)
    - 待機列の配列の生成は人物検出後の、グループ検出の前の段階で行う
    - 基準の時間以上(実際はミリ秒の閾値を使用して、FPSから割り出す)許容範囲内の割合(固定のピクセルではなく動いた割合、閾値)の位置に留まっていたら待機列判定(子アルゴリズム)
    - カルマンフィルター導入(子アルゴリズム)
    - 移動の検査の範囲はFPSや人物のバウンディングボックスのサイズから動的に求める(子アルゴリズム)
    - 前のフレームの周辺にある人物を色の検査にかけて、許容範囲内かも併用して判断する(子アルゴリズム)
      - 人物のポーズ検出で検出された体の部位ごとに、ポイントの周辺のピクセル(数ピクセルではなく`n x n`のような正方形などの領域)の色の平均を保持して、変化が許容範囲内か比較
      - その色の判定用の領域は固定サイズではなく、バウンディングボックスのサイズから動的に決めて、移動時のカメラからの距離によるサイズの変化に対応する
      - 色の探索の領域の大きさはバウンディングボックスのサイズから決まるため、FPSは関係ない
      - 人物から探索の領域を切り取ったら、色の抽出の段階では固定サイズのキャンバスを使い回し
        - imageHelperのメソッド(OOM対策済み)で画像を切り取る
      - 手足など変化が激しい部位もあるので、胴体の四隅(両肩、腰の左右)と、顔を対象にする
      - 胴体の四隅(両肩、腰の左右)は四角形(胴体)の内側を対象にする(外側の部分を含むと変動が激しくなり機能不全になるため)
      - 後ろ姿も考慮して、顔の特徴は体の向きごと(前・後ろ)に分けて保持する
      - 部位の色は一定の信頼度を超えたら新しい情報を使用
      - 影や照明の影響を抑えるため、色空間はRGBではなくHSVを使用し色味成分で比較
      - 彩度によって、色相と明度の重みの割合を変化させる
      - よって色相(H)は彩度(S)に連動して判断の厳しさを調整
      - また、無彩色などでは色相よりも明度の比重が高くなる
  - 数フレーム以上(FPS連動)見失ったら追跡の配列(`TrackedPerson`を保持しているやつ)から人物削除(OOM対策で配列は使いまわされる)
  - 人物の追跡で情報を保持する`TrackedPerson`クラスを追加
    - 追跡に使うID(念のためUUID、`crypto.randomUUID()`で十分)を持つ(コンストラクタで生成される)
    - フレーム更新時に状態を伝えるメソッド(`Person`や、タイムスタンプもこれで渡す、オブジェクトで`Person`は任意なので有無で見失ったかの判定も兼ねる)
    - 最新の人物(`Person`型)も持つ(見失っている時は`undefined`)
    - 人物の特徴量も持つ(読み取り専用、データは人物の更新時に一緒に更新される、色の抽出は別ファイルのメソッドに切り出された画像と`Person`を渡して行う)
    - 待機列判定の状態取得メソッドも持つ(`bool`)
    - 内部で見失った秒数(ミリ秒)を持つ
    - 削除するべきかの取得メソッドも持つ(`bool`、内部で判定)
    - 他から参照がないので`remove`メソッドは不要(配列から要素を削除で十分)
    - `Person`の取得メソッドで、返す時に`Person`にIDが追加される
  - `Person`型に、ユーザーがIDを確認することができるように追跡で使われるIDも追加(既存のプロパティと同じく任意)
  - 毎フレームの処理後、待機列の人物が入った配列がそのままグループ検出に渡される(`bool`の状態で待機列の人物のみに絞られる)
  - getGroups (ルート)
    - utils
      - imageHelper (使用するだけ)
      - ringBuffer.ts (新規、32ビットと64ビットのリングバッファのクラス、`Float32Array`や`Float64Array`の使い回しなどのOOM対策が保証されている)
    - index.ts (トラッキングのステップを追加)
    - types/person.ts (Person型にプロパティ追加)
    - steps/trackPeople
      - index.ts (呼び出し用、ここで呼び出された時の`performance.now()`を確定)
      - measureFps.ts (どこから呼び出しても共通)
      - TrackedPerson.ts
      - trackPeople.ts (トラッキング処理の中核)
      - extractFeatures.ts (色などの特徴を抽出するメソッド)
      - KalmanFilter.ts (新規、カルマンフィルターのクラス、内部で`Float64Array`のリングバッファのクラスを使用)

## 注意事項
- 連続稼働でOOMを防ぐため、全ての前後や現在の検出結果はスコープ外で変数を宣言して使い回し
- 各自解放処理忘れずに実装
- 基準・閾値の定数は全て大文字のスタイル
- ラッパーが呼ばれるときに、FPS推定のため呼び出された時間(`performance.now()`)をグローバルで保持して、平均で何秒間隔で呼び出されるか(FPS)を求めて、移動を検出する範囲などで活用(初回フレームの精度は諦めるのでこれでいい)
- FPSは常時更新
- 「子アルゴリズム」というのは、アルゴリズム内で使用する、さらに独立したアルゴリズム
- アルゴリズムの数式はLaTeXの構文でコード中にメモ
- それよりも詳しい内容を別ファイルにマークダウンにしてメモ
